⚠ 필드명이 `checkingTrends` 지만 **외화 KRW 환산까지 포함한 총현금**이다 — 8/21 값

## 비교 방식 — 레벨이 아니라 일별 증감

`FX_ADJ` 가 **날짜 없는 상수**로 전 구간에 얹히므로(index.html 5155 의 의도된 절충) 레벨
차이는 언제나 약 −1.26억이 깔린다. 증감으로 보면 그 상수가 상쇄돼 **특정 날짜에만 튀는
차이 = 그 날의 실제 데이터 문제**가 드러난다.

거래가 아니라 보유 외화의 환율 재평가다. 대시보드는 이걸 일별로 추적하지 않는다.

### 조치 완료 — fxAdjAt(date) 도입 (2026-08-23)

`FX_ADJ` 를 상수에서 **날짜별 배분**으로 바꿨다. `index.html` 의 `buildFxRamp_` / `fxAdjAt` /
`fxAdjTail`, 테스트는 `scripts/test-fx-adj-at.mjs` (19/19).

**배분 규칙 2가지**
1. `fx_adjust_base.through`(=2026-06-30) 까지는 **0**. 그 구간은 `pre_krw` 가 장부를 평가액에
   맞춰 둔 구간이다(그 note 의 "대조 검증 오차 −69,216원").
2. through 이후는 **환전 시점에 실현된다.** USD 입금이나 USD 직접지급은 장부와 평가를
   어긋내지 않는다 — 환율이 다른 환전이 어긋낸다. 그래서 through 이후 `fx_usd` 행 중
   환전 성격(`계좌간이체`·`외환차손`)만 |금액| 비중으로 램프를 만든다.

**부수 효과 — '현금 마이너스' 표시가 사라졌다**
총자산 구성 차트에서 연초~5/20 사이 **40일이 마이너스로 계산되고 있었다**(3/10 −0.89억 등).
실제 바닥이 아니라 이 버그의 산물이었고, 도입 후 **음수일 0일**이 됐다
(3/10 +0.36억 · 3/17 +0.70억 · 5/15 +0.78억 · 5/20 +0.59억).
2026-08-22 에 차트에서 지운 '현금 마이너스' 안내가 가리켰던 현상 자체가 버그였다.

**적용 지점** — 과거 날짜를 그리거나 집계하는 곳만 바꿨다. 오늘 기준으로 누적하는 곳
(`renderBankRecon` 의 `calc`, KPI 의 `cash`, 궤적 시작점)은 `fxAdjAt(오늘) === FX_ADJ` 라
손대지 않았다.

| 함수 | 무엇 |
|---|---|
| `renderCashChart` | 일별 잔액 추이 (기준일−90일 ~ 기준일) |
| `renderAssetMixChart` | 총자산 구성 (연초 ~ 오늘) — 영향이 가장 컸다 |
| `calcKPIs` | **현금 잔액 KPI 카드** — `cash` 는 `ref`(보고기준일)까지 누적한다 |
| `renderRegularReport` | 정기보고 현금·런웨이 — 같은 이유 |
| 월간 KPI/생키 | `pmEndCash`·`mEndCash` |
| 주간 리포트 | `pwEndCash`·`wkEndCash` |
| `computeWeeklyCashSeries` | `fxAdjBefore` 인자 추가 — 주차 시작 시점과 오늘의 조정이 갈린다 |

### ⚠ 첫 구현에서 놓쳐서 화면이 어긋났던 것
`calcKPIs` 와 `renderRegularReport` 의 `cash` 를 "오늘 기준"으로 착각해 손대지 않았다.
실제로는 **`refDate` 까지 누적**한다. 그래서 보고기준일을 과거로 옮기면 **추이 차트는 고친 값,
KPI 카드는 옛 값**이 나와 1.26억 갈렸다 — 대표님이 바로 발견했다.
교훈: `INIT_CASH + FX_ADJ` 를 쓰는 지점은 누적 상한이 `today` 인지 `ref` 인지 **반드시 확인**할 것.
`ref` 면 `fxAdjTail(ref)` 보정이 필요하다.

검증: 보고기준일 1~8월 8개 지점에서 KPI 경로와 차트 경로가 **전부 0원 차이**로 일치한다.

**⚠ 안전장치** — `through` 가 없거나 through 이후 환전 행이 없으면 램프를 만들지 않고
**종전처럼 상수로** 동작한다. 분류 체계가 바뀌어 환전 행을 못 찾을 때 과거 잔액을 조용히
왜곡하지 않기 위한 것이다. 환전을 다른 중분류로 분류하게 되면 `FX_CONV_MIDS` 에 넣어야 한다.


## 현금 시계열 시작일을 2026-01-01 로 이동 (2026-08-23)

### 왜 — INIT_CASH 가 '기초잔액'이 아니었다

| | 금액 |
|---|---|
| 클로브 실제 2025-10-23 잔액 | **2,240,314,236** |
| 종전 `INIT_CASH` | 477,006,675 |
| 차 | **−1,763,307,561** |

cf_data 의 2025년 행은 **라오스 지출 4건(−328,588,261)뿐**인데 클로브 실제로는 10/24~12/31 에
−2,091,350,302 이 움직였다. **2025년 활동 약 17.6억이 미기록**이고 `INIT_CASH` 가 그걸 통째로
흡수하고 있었다. 이름과 실체가 달라 오해를 부르는 상태였다.

### 무엇을 했나

- `settings.cf_start = '2026-01-01'` 신설. 이 날짜 이전 행은 **현금 계산에서 제외**된다.
- `settings.init_cash = 148,963,934` — **클로브 실제 2026-01-01 개시 잔액**. 이제 보정상수가
  아니라 관측값이다.
- 2025년 라오스 4건은 **라오스 누적 투입 계열에는 그대로 남는다**(투입 누계라서). 현금에서만 빠진다.

### 어떻게 — 루프를 안 건드렸다

`initCashEff()` 하나를 만들고 `INIT_CASH + FX_ADJ` 라는 **한 패턴만 13곳 치환**했다.
그 함수가 시작일 이전 행의 효과를 기초에서 미리 걷어내므로, 결과적으로
`balance(cf_start) === init_cash` 가 된다.

**루프마다 날짜 조건을 넣지 않은 이유**: 현금을 누적하는 곳이 열 군데가 넘고, 같은 날 fxAdjAt
을 넣을 때 그중 둘(`calcKPIs`·`renderRegularReport`)을 빠뜨려 화면이 갈린 적이 있다.
한 패턴만 치환하면 빠뜨릴 수가 없다.

### ⚠ 545,520 은 '어디에 두든 존재하는 잔차'가 아니었다 (2026-08-24 정정)
당시 나는 "8개월 누적 잔차(대부분 외화 재평가)라 어디에 두든 존재한다"고 적었다. **틀렸다.**

항등식으로 보면 명확하다. 1/1 을 정확히 맞췄으므로
```
diff(오늘) = FX_ADJ − (클로브 실제 순변동 − cf_data 기록 순변동)
```
| | 금액 |
|---|---|
| 클로브 실제 순변동 (1/1→8/21) | 559,611,668 |
| cf_data 기록 순변동 | 685,993,248 |
| cf_data 과대기록 = FX_ADJ 가 설명해야 하는 양 | **−126,381,580** |
| 당시 FX_ADJ | −125,836,060 |
| 남는 것 = diff | **−545,520** |

즉 **`pre_krw` 가 545,520 틀려서 FX_ADJ 가 그만큼 부족했던 것**이다. `pre_krw` 를 올바른 값
114,935,167(6/30 이전 미태깅 외화 14건의 합)로 고치니 **8/21 차이가 402원**이 됐다.
1/1 은 그대로 0 이다. 상세는 `docs/clobeid-backfill-progress.md` 의 pre_krw 정정 절.

## 2025년 미기록 643건 — 보류 (2026-08-24)

`cf_start = 2026-01-01` 이 2025년을 현금 계산에서 잘라내고 있으므로 **지금 상태로 깨진 데는
없다.** 필요해지면 그때 넣는다.

### 준비는 끝나 있다 — 기존 4건에 clobe_id 를 붙여 뒀다

이게 중요하다. 그 4건은 **수기 입력분이라 적요가 클로브와 다르다**(cf 는 라오스 거래처명,
클로브는 지출 목적). push 의 중복판정은 clobe_id 가 없으면 (거래일+적요+금액+상태)로
떨어지므로, 그대로 재적재하면 **금액이 같은데도 적요가 달라 중복 4건이 생긴다** —
2026-01-28 에 실제로 났던 사고와 같은 종류다. 미리 붙여 두었으므로 이제 안전하다.

### 넣을 때의 방법 (권장 순서)

1. **클로브 웹(app.clobe.ai)에서 엑셀 export** 를 받아 스크립트로 적재한다.
   643건 × 6필드 ≈ 3,900 값을 손으로 옮기는 것보다 안전하다 — 법인카드·H201 에서 쓰는 방식.
   MCP 로 7페이지 받아 전사하는 방법도 되지만 20턴쯤 걸리고 적요·거래처까지 옮겨야 한다.
2. 분류는 cf_data 2026년에 이미 있는 적요·거래처 → 중분류 패턴을 적용한다(성격 추론 금지).
3. 검증은 클로브 일별 잔액(2025-09-22 부터 확보 가능)과 대조한다.
4. 다 끝나면 `cf_start` 를 **2025-10-24**, `init_cash` 를 그날 실잔액 **2,240,314,236** 으로
   옮긴다(`setMeta`).

### ⚠ 일부만 넣지 말 것
현금 시계열은 그 기간 거래가 **전부** 있어야 맞는다. 643건 중 일부만 넣으면 2025년 현금선이
'그럴싸하지만 틀린' 모양이 된다. 전부 넣거나, `cf_start` 로 잘라낸 지금 상태를 유지하거나 둘 중
하나다.
