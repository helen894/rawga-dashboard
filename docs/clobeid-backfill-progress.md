# 2026-03~06 clobe_id·tx_at 백필 진행 표식

**목표**: 2026-03-01 ~ 06-30 실거래 1,044건에 `clobe_id`·`tx_at` 을 붙인다.
**방식**: 재적재 금지. `cf-clobeid-backfill.mjs` 로 기존 행에 두 필드만 patch(멱등).

## 왜 재적재가 아닌가

3~6월은 `clobe_id` 가 전무해서 push 의 중복 판정이 (거래일+거래내용+금액+상태) 로 떨어진다.
기존 적요는 은행 원본 문자열(`스마트스토어정`·`신동섭`·`(유)바다향`)이고 적재는 거래처명을
넣는다(`네이버파이낸셜 주식회사`·`은혜수산`·`바다향`). 같은 거래인데 문자열이 달라 안 걸린다.
**실측: 재적재하면 667건(63.9%)·408.5억이 이중계상된다.** 2026-01-28 에 실제로 1건 났다.

## 이어받는 방법

```bash

#    get_labeled_transactions  startDate/endDate/size=100, hasNext 면 cursor 로 끝까지

# 3) dry-run → 확인 → --apply
```

## 끝나고 한 검증 — 결과

**백필은 금액 합계 검증에 걸리지 않는다.** `clobe_id` 를 붙일 뿐 금액을 안 바꾸므로,
잘못된 id 를 붙여도 잔액·집계는 그대로 맞는다 — **틀려도 조용하다.**
그래서 구조로 잡았다(API 재조회 없이 되는 것들, `/tmp/verify-ids.mjs` 로 실행):

| 검사 | 결과 |
|---|---|
| clobe_id 중복 | ✓ 없음 (2026-01~08 전체 1,982건) |
| tx_at 날짜 == date | ✓ 불일치 없음 |
| 신한 56019 id 수열 연속성 | 구멍 8건 → 4건은 분할(정상), **4건은 누락** |
| id 순서 vs tx_at 순서 | ✓ 역전 없음 |
| cf_data 0건인 날 52일 전수 대조 | 1/31~2/1 외 전부 클로브도 0건 |

**금액·날짜는 별도로 이미 검증됐다.** 매칭이 (날짜+금액)으로 이뤄지므로, TSV 전사 중
금액을 오타냈으면 그 행은 매칭 실패로 떠올랐을 것이고, 실제로 떠오른 모든 행은
분할·외화·취소·동일행으로 설명이 끝났다.

**남은 사각지대**: id 수열이 없는 계좌(87970·56023·56033 등)에서 id 만 오타 나고 금액은
맞은 경우. 이건 클로브 API 를 전 구간 재조회해 id 집합을 대조해야 잡힌다 — 미실시.

### ⚠ 2와 3은 서로 얽혀 있다 — 따로 뽑은 값을 같이 넣으면 안 된다
`FX_ADJ = fxKrw − (pre_krw + Σfx)` 이므로 `pre_krw` 를 낮추면 FX_ADJ 가 같은 만큼 올라가고
잔액도 올라간다. 그래서 `init_cash` 도 같은 만큼 더 낮춰야 한다.

앞서 대기 중이던 값은 `init_cash 458,716,508` + `pre_krw 114,390,049` 였는데,
**458,716,508 은 pre_krw 를 안 바꾼 상태로 뽑은 값이었다.** 둘을 같이 넣으면 659,918 이
이중반영된다. 확정값의 유래:

```
458,716,508  (종전 대기값, pre_krw 미변경 기준)
 + 18,950,085  1/31~2/1 누락 5건 적재로 잔액이 그만큼 낮아짐
 −    659,918  pre_krw 인하로 FX_ADJ 가 그만큼 올라감
= 477,006,675
```

### Edge 에 setMeta 액션을 추가했다
`cat_data` 는 RLS 때문에 publishable 키로 못 쓴다. 조회는 `inspect.meta` 로 뚫려 있었지만
쓰기는 `mid_to_big` 병합밖에 없어서, 스크립트로 역산한 값을 화면 로그인 없이 반영할 수단이
없었다. 그래서 좁은 경로를 하나 뒀다:

```bash
# dry 로 before/after 확인 → --apply
{ secret, setMeta: { "settings.init_cash": 477006675,
                     "fx_adjust_base.pre_krw": 114390049 }, dry: true }
```

**일부러 화이트리스트로 막았다.** 허용 경로는 위 둘뿐이고 숫자만 받는다 — "cat_data 아무
키나 쓰기"로 만들면 이 함수가 SERVICE_ROLE 범용 쓰기 도구가 되고 오타 한 번에 학습
매핑·일별설정이 날아간다. 행이 없으면 만들지 않는다(mergeMidToBig 와 같은 이유:
여기서 만들면 그 키의 다른 필드가 통째로 사라진다). 낙관적 잠금·멱등(같은 값이면
