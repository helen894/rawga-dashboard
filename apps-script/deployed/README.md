# apps-script/deployed — 구글에 실제로 들어 있는 소스

여기 있는 파일은 **Apps Script 프로젝트에서 그대로 내보낸 것**이다. 손으로 고치지 않는다.
위 디렉터리(`apps-script/*.gs`)가 우리가 편집하는 사본이고, 여기는 **대조용 거울**이다.

회수 방법 (브라우저에서 구글 계정으로 로그인한 상태에서):

```
https://script.google.com/feeds/download/export?id=<스크립트ID>&format=json
```

받은 `.json` 을 `scripts/`(없으면 임시 스크립트)로 풀면 `appsscript.json` + `Code.gs` 가 나온다.
스크립트 ID 는 드라이브에서 `mimeType = 'application/vnd.google-apps.script'` 로 찾는다.

| 폴더 | 프로젝트 이름(드라이브) | 짝이 되는 편집 사본 |
|---|---|---|
| `cf-folder-ingest/` | `CF 자동적재` | `../cf-folder-ingest.gs` |
| `clobe-drive-bridge/` | `제목 없는 프로젝트` (2026-11-13 생성) | `../clobe-drive-bridge.gs` |
| ⤷ 같은 프로젝트의 둘째 파일 | | `../clobe-direct-ingest.gs` (2026-11-20 추가, **미회수**) |

⚠ 이 거울은 **2026-11-17 회수분이라 이미 낡았다.** 아래 '2026-11-20' 절이 그 뒤의 변화다.
다음에 손댈 때 제일 먼저 재회수할 것.

`ar-sheet-sync.gs` 는 스프레드시트에 묶인(container-bound) 스크립트라 위 검색에 안 잡힌다. 미회수.

## 2026-11-17 회수에서 드러난 것

### ⚠⚠ 1. 배포본은 **어느 소스에도 없는 코드**로 돌고 있다

> **그 뒤 (2026-11-20):** 진입점을 소스에 되살려 저장소에 넣었다(`5ce0837`). 다만 **구글 쪽
> 소스에는 아직 안 붙여 넣었으므로 어긋남은 그대로다.** 바뀐 건 위험의 크기뿐이다 —
> 이 진입점을 치던 '지금 가져오기' 버튼을 대시보드에서 없앴고(`f27b7c7`), 그 폴더를
> 들여다보던 10분 트리거도 지웠다. 즉 지금은 **아무도 안 쓰는 배포**라 깨져도 티가 안 난다.
> 되살려 쓸 일이 생기면 저장소 사본을 붙여넣고 **새 버전으로 배포**해야 한다.

대시보드의 **'지금 가져오기'** 버튼은 `CF 자동적재` 의 웹앱 `/exec` 주소를 친다.
그 주소에 GET 하면 `ingestNewFiles()` 의 반환문(`처리할 xlsx 파일이 없습니다.`)이 그대로 온다 —
즉 **웹앱 진입점(`doGet`/`doPost`)이 분명히 있다.**

그런데 **`CF 자동적재` 프로젝트의 현재 소스에는 `doGet`·`doPost` 가 없다.**
(같이 내보내 확인한 `clobe-drive-bridge` · Wellness Pack 폼에도 없다. `ingestNewFiles` 는
`CF 자동적재` 에만 있으므로 그 `/exec` 는 이 프로젝트의 배포가 맞다.)

결론: 배포는 **옛 버전에 얼어붙어** 있고, 그 버전에만 있던 진입점이 이후 소스에서 지워졌다.

왜 위험한가:
- **아무도 그 코드를 재현할 수 없다.** 지금 도는 건 되돌릴 수 없는 스냅샷이다.
- 그 프로젝트를 **다시 배포하는 순간 버튼이 죽는다.** 현재 HEAD 에는 진입점이 없으니까.
- 그런데 **대시보드는 그걸 알아챌 수 없다** — `fetch(..., {mode:'no-cors'})` 라 응답을 못 읽는다.
  버튼은 언제나 "새로 가져온 내역이 없습니다" 로 끝난다. 성공과 고장이 같은 화면이다.

되살리려면 Apps Script 편집기 → 배포 관리 → 버전 기록에서 옛 버전 소스를 꺼내거나,
진입점을 새로 써서 소스에 넣고 재배포해야 한다(그래야 재현 가능해진다).

### ⚠ 2. `cf-folder-ingest` 는 **저장소가 구글보다 최신**이다

예상과 반대였다. 저장소 사본에만 있는 것:

- `desc_alt` 폴백 — 적요가 빈 행에서 `거래자명/거래자/예금주/상대방` 을 대신 쓴다.
  클로브 계좌간이체처럼 적요가 공란인 행이 `(거래내용 없음)` 으로 들어가던 걸 막는 개선인데,
  **구글 쪽에는 반영돼 있지 않다.** 지금 도는 xlsx 적재는 이 폴백 없이 동작한다.
- `clever-endpoint` 슬러그에 대한 주석

즉 저장소 → 구글 방향으로 붙여넣기가 필요하다(이번 회수에서는 하지 않았다 — 회수만 요청받았다).

### 3. `clobe-drive-bridge` 는 일치한다

줄 끝 개행 하나 빼고 저장소 사본과 같다. 손댈 것 없다.

## 2026-11-20 — 구글 쪽에서 바뀐 것 (여기 거울에는 아직 없음)

클로브 MCP 가 **표준 OAuth 보호 리소스**인 것이 확인돼(= Apps Script 가 직접 읽는다),
07:00 적재에서 드라이브 경유를 걷어냈다.

```
이전:  클라우드 루틴 → 드라이브(대기) → 브리지(10분) → Edge → cf_data
이후:  Apps Script 트리거 ───────────────────────→ Edge → cf_data
```

| 바뀐 것 | 어디 |
|---|---|
| `clobe-direct-ingest.gs` 새 파일 + 웹앱 배포(액세스 **모든 사용자**) | `제목 없는 프로젝트` |
| `runDailyDirectIngest` 트리거 신설 — `atHour(7).nearMinute(0)` = **06:45~07:15** | 〃 |
| 드라이브 xlsx 를 보던 **10분 트리거 삭제** (2026-07-31 이후 빈손으로 약 17,000회 돌았다) | `CF 자동적재` |
| 대시보드 '올려둔 엑셀 적재' 버튼 제거 | `index.html` |

⚠ **`대기` 폴더에 쓰지 말 것.** 직접 적재는 원본을 `완료`(성공)·`보류`(실패)에만 남긴다.
`대기` 에 쓰면 브리지가 집어가 **같은 거래를 두 번 넣는다.**

⚠ **트리거는 저장된 코드를 바로 쓰고, 웹앱 버튼만 배포 버전을 본다.** 트리거 쪽만 고쳤으면
재배포가 필요 없고, 버튼 동작을 바꿨으면 새 버전으로 배포해야 반영된다. 이 둘을 섞으면
"고쳤는데 왜 그대로지" 가 된다 — 위 1번 항목이 바로 그 사고였다.

**아직 확인 안 된 것:** 브리지 자신의 10분 트리거(대기→Edge)가 남아 있는지. 남아 있어야
클라우드 루틴 쪽 결과가 계속 들어와 **며칠간의 양쪽 대조**가 성립한다. 내일 아침 `대기` 폴더에
파일이 쌓여 있으면 그 트리거가 없는 것이다.

## 2026-11-23 — 예약을 07:00 1회 → 07:00·11:30·16:30 3회로 (⚠ 구글에 **아직 안 붙여넣음**)

### 무엇이 문제였나

11/18~20 사흘을 클로브 원본과 대조하니 **건수·금액 전건 일치**였다. 적재는 멀쩡했다.
문제는 **시각**이었다.

```
07:00  우리 예약 실행      ← 여기서 읽으면 클로브는 아직 어제치다
09:13  클로브가 그날 수집
```

그래서 11-23 07:06 에 빠진 비씨카드 대금 **6,148,296** 이 그날 대시보드에 안 들어왔다.
적재 로그는 `· 2026-11-23 거래 없음` 이었다 — **'정말 거래가 없었다' 와 똑같은 글자다.**
매일 '성공' 으로 끝나면서 숫자만 하루 늦는, 제일 알아채기 어려운 고장이다.

### 무엇을 바꿨나 (`../clobe-direct-ingest.gs`)

| | |
|---|---|
| 예약 | `atHour(7)` 1회 → `DIRECT_DEADLINES = [[7,0],[11,30],[16,30]]` 3회 |
| 지연 표시 | 머리줄에 `⚠ 클로브 수집이 N일 전(날짜)` — 웹앱 `doGet` 에 그대로 나온다 |
| 속성 | `DIRECT_LAST_ASOF` 추가 (`2026-11-23 (당일)` 형태) |
| 알림 | 수집이 **2일 이상** 멈추면 실패가 아니어도 메일 |
| 진입점 | `setupDirectTrigger` → **`setupDirectSchedule`** 로 개명 (아래 ⚠ 중복 사본) |
| 진단 | `checkCodeVersion()` — 지금 도는 게 새 사본인지 본다 |

예약표는 **마감 시각**으로 적는다 — 중심이 아니다. 구글은 분을 못 박아주지 않고
`nearMinute` 가 ±15분이라, 중심을 마감에 두면 **절반이 마감을 넘겨** 돈다.
그래서 중심을 마감 15분 앞에 두고(`triggerCenter_`), 구간이 마감에 맞아 끝나게 한다.
바꿀 땐 `DIRECT_DEADLINES` 만 고친다 — 숫자를 두 군데 적지 않는다.

| 마감 | 실제 구간 | 무엇을 집나 |
|---|---|---|
| 07:00 | 06:30~07:00 | 밤사이 재수집분. **보통 빈손**이고 '1일 전' 이 붙는 게 정상 |
| 11:30 | 11:00~11:30 | **본진** — 클로브 정기 수집(09:1x) 뒤라 오늘치가 처음 들어온다 |
| 16:30 | 16:00~16:30 | 장중 재수집분 |

⚠ 구간은 **시작** 시각이다. 적재 자체가 몇십 초 더 걸리고 구글은 과부하 때 트리거를
미룰 수 있다 — '마감' 은 약속이 아니라 목표다.

오후 회차가 헛돌지 않는 근거: 클로브는 정기 수집 말고도 다시 긁는다. 2026-11-23 에
`lastRequestedAt` 10:28 → 기업은행 6계좌가 **10:32 에 재수집**됐다(나머지는 09:1x 그대로).
클로브에서 '최신화' 를 누르면 그다음 회차가 알아서 집어 온다는 뜻이다.

판정은 `collectionLagDays_()` 로 빼냈고 `scripts/test-collection-lag.mjs` 가 32건으로 못 박는다
(월·연·윤년 경계, 판정 불가 시 0, 미래값 0, 예약표 3회, 마감→중심 환산, 자정 넘김 포함).
그중 **`클로브 수집(09:1x) 뒤에 시작하는 회차가 있다`** 가 핵심이다 — 회차를 어떻게 바꾸든
이게 깨지면 매일 어제치만 읽던 11-23 상태로 되돌아간다. 판정은 마감이 아니라 **가장 이른
시작(마감−30분)** 으로 한다. 마감으로 재면 11:30 짜리가 실제로는 11:00 에 돈다는 걸 놓친다.

### ⚠⚠ 구글 프로젝트에 **옛 사본이 남아 있다** (2026-11-23 확인)

새 코드를 붙여넣고 **저장까지 했는데도** `setupDirectTrigger()` 가 옛 메시지
(`06:45~07:15`)를 찍었다. Apps Script 는 파일이 여러 개여도 함수를 **한 바구니**에 담아서,
같은 이름이 둘이면 **하나만 이기고 경고도 없다.** 증상은 '고쳤는데 안 바뀐다' 뿐이다.

- 당장의 회피: 진입점 이름을 `setupDirectSchedule` 로 바꿔 싸움을 피했다.
- 진짜 해결: 그 **옛 `.gs` 파일을 지워야 한다.** 안 지우면 `runDirectIngest` 같은
  다른 함수도 옛 사본이 이기고 있을 수 있다 — `checkCodeVersion()` 으로 확인한다.

### ⚠ 반영하려면 두 단계

1. `apps-script/clobe-direct-ingest.gs` 전체를 구글 프로젝트에 붙여넣고 **저장**
2. 편집기에서 **`setupDirectSchedule()` 을 한 번 실행** — 옛 트리거를 지우고 3개를 건다
   (로그에 `06:30~07:00 / 11:00~11:30 / 16:00~16:30` 이 찍히면 성공)

2번을 빼먹으면 **코드만 바뀌고 트리거는 옛 시각 그대로**다. 트리거는 저장된 코드를 쓰므로
1번만으로도 새 코드가 돌지만, 도는 **시각**은 트리거에 박혀 있다.

끝나면 트리거 목록에 `runDailyDirectIngest` 가 **3줄** 이어야 한다. 그보다 많으면 옛 것이
남은 것이고, 하루에 여러 번 헛도는 회차가 생긴다.

재배포(새 버전)는 필요 없다 — 웹앱 버튼 동작은 안 건드렸다.

### 클로브 수집 시각이 바뀌면

`get_scraping_status` 의 `scrapedAt` 이 판단 근거다. 09:13 은 **하루치 관측**이라
고정값으로 믿지 말 것. 웹앱 `doGet` 의 `수집 기준` 줄에 매일 찍히므로 며칠 보고 조정한다.

## 다음에 이 폴더를 쓸 때

Apps Script 를 고칠 일이 생기면 **순서를 지킨다**:

1. 여기(`deployed/`)를 먼저 새로 회수해 구글의 현재 상태를 확인한다
2. 편집 사본(`apps-script/*.gs`)과 대조해 어느 쪽이 앞선지 본다
3. 고치고 → 구글에 붙여넣고 → **다시 회수해** 양쪽이 같아진 것을 확인한다

사본이 둘로 갈리면 조용히 어긋난다. 주간 리포트 메일 HTML 이 미리보기용·발송용 두 벌로
갈려 있던 것과 같은 함정이다(`rawga-weekly-email` 메모 참고).
